# End-to-end workflow

## Responsibilities
LangGraph is a bounded graph, not a free-roaming swarm. Research agent builds targeted queries and extracts source-backed findings. Analyst agent proposes candidate signals, role implications and offer fit. Writer agent produces the email using approved facts only. Critic agent checks entailment and flags unsupported wording. Python owns validation, scoring, budgets, routing, persistence, retries and review transitions. These are logical responsibilities; they do not require independent services.

## Execution
1. **validate**: FastAPI validates input, snapshots it, creates queued run/job and event in one transaction. Return immediately. Worker claims job and marks running.
2. **research**: query person+company+role, then company news/hiring/funding/interviews and offer-relevant developments. Prefer primary company announcements, official careers and attributable interviews; use reputable reporting for corroboration. Search public LinkedIn snippets only if available, never require login or scrape private pages. Save real provider tool activity and call IDs. A proposed maximum of four search requests, two bounded batches, 12 retained sources and 180 seconds limits runaway work; surface partial coverage.
3. **qualify_evidence**: extract atomic claims with source IDs and short supporting passages. Record publication date, event date and retrieval time separately. Verify person identity and company association separately from title equivalence and role currentness. An undated primary biography may establish identity/association and title wording, never present employment. Input role alone is not verification. Current role use requires a supported role claim, an explicitly corroborated full date within 180 days on primary evidence, and semantic currentness review. Identify conflicting employer, role, dates or event claims. Syndicated copies count as one origin. Unsupported snippets are leads, not verified claims. One targeted follow-up search may use the remaining search budget.
4. **evaluate_signals**: analyst connects each eligible event to verified prospect context and offer capability. If current role is unverified, evaluate independently verified company events without assuming employment, duties or authority; remove role claims and the input designation from reasoning and generation. Separate fact, inferred implication and seller hypothesis. Python applies the gates and scoring below; save rejected candidates with reasons.
5. **draft**: generate a concise subject and body with claim references and optional low-pressure CTA. No fabricated compliments, pain points, numbers, personal activity or guaranteed ROI. Role implications use qualified phrasing. UI renders reference links beside factual sentences and in a source panel.
6. **validate_draft**: Pydantic and Python check IDs, eligibility, empty fields and reference coverage; critic checks whether cited evidence supports the actual wording. One repair attempt within budget; unresolved support failures become failed with code draft_grounding_failed. No draft reaches review on an invalid result.
7. **await review**: publish immutable draft version and mark awaiting_review. SDR can save edits, regenerate, approve or reject. Approved content is available to copy manually. No send action exists.

## Evidence and selection policy (proposed defaults)
An eligible factual claim needs an accessible supporting passage supplied by research, matched entity and no unresolved material contradiction. LLM-generated research narration is not a source passage. If the provider cannot supply enough attributable evidence, abstain. Show excerpts conservatively, with source links; do not retain whole copyrighted pages.

An event signal needs a known event/publication date within 180 days; publication date used as proxy is labelled. Future announcements are labelled planned, never completed. Unknown dates cannot pass the freshness gate. Older sources can establish identity/context only. Evidence quality: 1.0 attributable primary source, 0.8 reputable independent reporting, 0.4 uncorroborated aggregator. Require quality ≥0.8 and one primary source or two independent reputable sources.

Analyst returns verified prospect relevance (legacy API field `role_relevance`) and offer fit as rubric integers 0–3 with evidence-backed explanations (0 none, 1 indirect, 2 clear, 3 direct). These are model judgments, not measured probabilities. Python requires both ≥2, identity confidence high, evidence eligibility and freshness. Compute score = 30×role/3 + 30×offer/3 + 25×quality + 15×max(0,1−age_days/180). Require score ≥70. Tie-break by quality, then event recency, then stable ID. Deterministic arithmetic does not make judgments objective. Persist rubric and prompt versions to explain results.

## Terminal decisions and precedence
Technical/provider failure → failed. Otherwise unresolved material identity or selected-claim conflict after follow-up → conflicting_evidence. Otherwise missing credible identity or usable evidence → insufficient_information. Otherwise no candidate passes freshness/relevance/score gates → no_relevant_signal. Otherwise draft passes checks → awaiting_review. Irrelevant conflicts on excluded candidates appear as warnings and need not block a valid alternative.

No personal activity or current-role proof is required for company-context evaluation when both person identity and company association are independently corroborated. A company-context draft must remain neutral about current employment, title, duties and authority. Insufficient identity/association still requires abstention. Signal thresholds are unchanged; lack of dated relevant events still prevents drafting. The quality auditor receives original passages for checking but may not reintroduce excluded role facts. Outdated evidence is shown but excluded; if all signals are stale the outcome is no_relevant_signal with reason outdated_only.

## State and human actions
Run statuses: queued, running, awaiting_review, approved, rejected, insufficient_information, conflicting_evidence, no_relevant_signal, failed. Stage is separate from status. Approval/rejection require the current draft version; approve validates saved edits again before committing. Unsupported manual facts can be saved as an unvalidated version but cannot be approved. Saving an edit creates a version, invalidates prior approval and sets awaiting_review. Reject records an optional reason and preserves evidence/drafts. Regenerate from awaiting_review/approved/rejected creates a new draft attempt, sets queued, uses existing eligible evidence with a freshness recheck and requires review again. Exhausted evidence requires a new full run. Reject/edit/approve while running returns 409. Failures preserve partial evidence and the last draft but never leave it approved.

## Execution integrity
Events are emitted on actual stage entry/completion or committed results, with real counts and timestamps; no fabricated timers or percentages. Worker leases and heartbeat detect crashes. Expired jobs are marked failed/worker_interrupted and may be retried explicitly through a new linked run. No unsafe automatic resume of partially committed graph nodes in the MVP. Provider 429/5xx/network errors get at most two bounded backoff retries within the total budget; authentication/schema failures fail promptly. All request attempts count against budgets.

## Independent identity policy — implemented 2026-11-26
New runs record `v2-independent-identity`. Four independent checks include their backing claim/source IDs and reasons in persisted evidence and the run API. One follow-up searches dated primary current-employment evidence; an existing qualified company event is preserved during source selection. Full dates must occur literally in retrieved page text; absent dates become unknown, never retrieval/copyright proxies. Current-role use additionally requires the date in its retained quotation. Scores disclose `verified_role` or `verified_company_context`; excluded role IDs are recorded. Historical records are not rewritten or automatically upgraded.
